# 新版逐轮情绪分析设计

## 目标与范围

每条被接受的新用户输入，在聊天回复生成前执行情绪分析，并将分析输入、参数、输出和可获取的失败信息持久化到 SQLite。分析使用当前会话截至本条输入的完整聊天历史。识别目标是本轮用户情绪，历史用于理解语境。

沿用归档 v1 的 32 类情绪并增加 neutral，共 33 类。标签及描述、family 映射分别使用独立 JSON 配置。此次实现不移植 v1 的记忆系统、风险路由或界面改版。

## 已确认行为

- 每条新消息分析一次，不设置轮次间隔，不复用上轮情绪作为本轮判断。
- 相同 request_id 的重复请求复用已有处理记录；不同 request_id 即使文本相同也重新分析。
- 历史限于当前 conversation_id，按 sequence_no 排序，包含截至当前输入的所有用户消息和已完成助手回复。保留角色，当前输入出现一次；不包括未来消息、未完成助手占位或其他会话。
- 情绪分析不受聊天回复的 context_message_limit 限制，不摘要或截断。超过服务上下文上限时记录失败并继续普通回复。
- 分析失败时保存可获取的失败信息，继续普通回复，本轮不注入旧情绪。

## 配置文件

默认配置放在受版本控制的 config/ 目录，避免依赖原工作区未提交的 data/ 内容。

`config/emotion_labels.json` 是“情绪标签：描述”的对象，包含全部 33 类。例如：

```json
{
  "sad": "一般性的悲伤、难过或低落。",
  "anxious": "对不确定结果感到担忧和不安。",
  "neutral": "当前输入没有明确情绪表达，以事实、日常问候或任务陈述为主。"
}
```

`config/emotion_families.json` 是“情绪标签：family”的对象，沿用 v1 的 family 标识，并为 neutral 增加 neutral family。例如：

```json
{
  "sad": "sadness_loss",
  "lonely": "sadness_loss",
  "anxious": "future_fear",
  "apprehensive": "future_fear",
  "neutral": "neutral"
}
```

示例仅展示结构，交付配置必须覆盖全部 33 类。family 只用于归类和查询，不替代主情绪标签。主情绪对应的 family 由程序查表派生，避免模型输出不一致。

允许通过环境变量分别指定配置路径。加载时拒绝重复键、空标签、空描述、空 family，以及映射缺失或多余标签。服务启动时加载并校验，修改后重启生效；每次调用保存配置内容快照及内容哈希，不以文件路径作为唯一追溯依据。

## 图与模块边界

主图调整为 prepare_turn → analyze_emotion → generate_response → finalize_turn。analyze_emotion 调用可独立测试的情绪子图：prepare_analysis → call_emotion_model → persist_analysis → END。持久化失败进入基础设施失败处理，不继续生成无法满足留痕要求的回复。

新增情绪配置加载器、提示词构造器、结果解析器和分析仓储。图状态传递 analysis_id、分析状态及经校验的结果，不把全量历史和调用轨迹重复塞入 checkpoint。SQLite 业务记录是审计事实来源。

成功时将本轮经校验的情绪及回复建议加入回复上下文；失败时不添加情绪上下文。聊天回复继续使用原有历史窗口设置。

## 分析方法与输出

使用独立情绪模型调用，支持 EMOTION_LLM_* 配置；未覆盖的连接配置沿用聊天模型。默认情绪温度建议为 0，记录实际有效参数。

提示词明确目标是最后一条用户输入，将 33 类标签及描述填入，并保留完整历史的角色边界。沿用 v1 的动态 few-shot 方案：最多选择 4 个示例，使用加权词项重合度及近期成功情绪先验加分；示例库、检索算法版本、候选先验、所选示例、分数及参数均形成调用快照。neutral 示例一并补齐。先验仅辅助判断，不代替本轮识别。

输出字段沿用 v1：primary_emotion、confidence、secondary_emotions、evidence、reply_strategy、trajectory_note、safety_level；补充由配置派生的 primary_family。confidence 是模型自报值。校验主次标签属于本次配置，confidence 在 0–1 之间，safety_level 属于 normal/supportive/crisis。无明显情绪可选 neutral；模型失败不能伪装为 neutral。

模型原始输出与解析结果分别保存。格式错误或校验失败记录为分析失败，不悄悄替换为默认情绪。本期 safety_level 作为分析结果和回复参考保存，不新增独立危机分支。

## 数据库与调用生命周期

新增 emotion_analyses 表，关联 user_message_id、conversation_id、request_id；user_message_id 唯一，保证每条输入只有一条逻辑分析记录。支持从当前 schema version 1 增量迁移，保留现有消息和数据，不对旧消息自动回填分析。

保存以下数据：

- 身份和状态：analysis_id、关联 ID、pending/running/completed/failed、创建/开始/结束时间。
- 输入快照：实际模型消息、历史消息 ID 和序号、完整提示词与模板版本。
- 配置快照：标签描述、family 映射、哈希、示例库和选择结果、先验和检索参数。
- 调用快照：provider、请求模型、服务地址、temperature、timeout、重试策略及所有显式传入的有效参数；服务端未公开的默认值不声称已知。
- 输出：原始内容、模型实际返回的推理内容、结构化结果、返回模型标识、响应元数据、finish_reason。
- 运行事实：token 用量、耗时、失败阶段、异常类型、错误码和信息、可获取的 HTTP 状态码及服务端请求 ID。无法获取的字段为 NULL。

情绪调用输入和参数在发起请求前提交到数据库，结束后提交结果，成功落库后才进入回复。凭据、Authorization 等敏感连接信息脱敏；不主动生成模型未返回的推理内容。

本期不自动重试情绪模型调用，并显式关闭适配器隐式重试，以保证一次调用的审计边界明确。失败后直接继续普通回复。以后增加重试时需引入逐次 attempt 记录，不覆盖旧失败。

启动恢复时将遗留 running/pending 分析标为中断失败，保留此前已持久化内容；消息恢复沿用项目现有机制，不承诺崩溃后自动继续回复。正常捕获的超时、模型错误、解析错误均按约定继续普通回复。

数据库写入本身失败时，无法保证失败信息入库，应走现有基础设施错误路径并输出脱敏日志，不谎报记录成功。该情况与模型分析失败区分处理。

## 验证与交付

- 配置加载：33 类完整、neutral、family 覆盖、非法 JSON、重复键及空值。
- 图顺序：每条新输入先分析并落库，再调用回复模型；成功使用本轮结果，失败继续普通回复。
- 完整历史：超过 40 条仍全部进入情绪调用；角色与顺序正确；当前输入不重复；不跨会话或包含未来消息。
- 审计：输入和参数在调用前可查询；成功和各类失败均保存可获取事实；空缺用 NULL；凭据脱敏。
- 幂等与恢复：重复 request_id 不重复分析；同文新请求重新分析；中断记录可恢复为失败。
- 迁移：旧数据库增量升级且原消息保持不变；持久化错误不能被误报为成功。
- 回归：运行现有测试及新增行为测试，以假模型测试为主，不依赖真实 API。

本设计基于 main 的已提交 HEAD e968014。原工作区存在提示词配置和相关测试等未提交改动，不复制或提交这些内容。实现以隔离 worktree 为准；将来整合时需要保留用户已有提示词配置能力。

## 方案取舍

采用独立分析表和情绪子图，便于逐轮查询、失败审计和独立测试。将分析塞进助手消息 trace 虽然改动更少，但会混合两次模型调用的状态与参数；移植整个 v1 则超出当前范围。因此采用前者。
